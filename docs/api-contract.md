# First milestone API contract

JSON API, same origin; errors `{ error: string, code?: string }` with appropriate HTTP status (including authentication, permission, conflict, validation, throttling and server errors). Shared content types are in `shared/types.ts`, authentication types in `shared/auth.ts`, and policy types in `shared/policy.ts`. GET returns objects directly; mutation returns created/updated object, except revision creation and version creation return `RevisionDetail`. Revision IDs `D1` for code and `P1` for papers, `L1` for prose/legal drafts (shared numeric sequence allowed), tasks `T1`, projects `PROJ1`, repositories `R1`, wiki `W1`, Spaces `S1`.

Paths below are relative to the configured `APP_BASE_PATH` (default `/`). For example, `/workspace/` places the health route at `/workspace/api/health`; requests outside the configured mount return 404. The bare mount redirects GET/HEAD to its canonical trailing slash. Frontend build and server mount must agree; a mismatch returns 503 with rebuild guidance. Mount support preserves the local-only security boundary.

- `GET /api/health` → `{ok:true}`
- `GET /api/state` → AppState; includes visible objects and filtered recent activity, visible Spaces, a member directory, object access descriptions, access epoch, currentPrincipalId, visible followingTaskIds, visible followingRevisionIds and creation capability
- `GET /api/notifications?filter=all|unread|read&before=OPAQUE&limit=N` → private `NotificationInbox`; `GET /api/notifications/count` → visible unread count and observed horizon. Read-scoped authority and current object View apply.
- `POST /api/notifications/read` → content-free immutable receipt for `read`, `unread`, `read_through` or `read_object`; requires write-scoped authority, Idempotency-Key and access/read pins, never object Edit. Automatic object-read marking is an explicit foreground POST, not a GET side effect. See [notification limits and recovery](notifications.md).
- `POST /api/tasks` TaskInput → Task with `projectIds`; creation accepts `projectIds` or the legacy scalar `projectId` alias, never both; `PATCH /api/tasks/:id` UpdateTaskInput (expectedVersion required; project fields use the separate tag action) → Task or a content-free TaskAccessLostAcknowledgement after a fresh owner change removes the caller’s view access
- `POST /api/tasks/:id/projects` TaskProjectsInput → TaskDetail; add/remove explicit tags or deliberately replace all tags, including omitted hidden associations; current task version and edit access, selected project visibility, local-mode offline replay supported
- `GET /api/tasks/:id` → TaskDetail; current fields, first history page, visible dependencies, duplicate relationships and inverse links
- `GET /api/tasks/:id/history?before=N&limit=N` → TaskHistory; newest-first exclusive sequence cursor, default 50, maximum 100, visibility filtering before pagination
- `POST /api/tasks/:id/comments` `{body}` → TaskTransaction (201); append-only discussion with interact permission
- `POST /api/tasks/:id/dependencies` TaskDependencyInput → TaskDetail; online-only directed edge change, source edit and destination view, atomic inverse history and cycle rejection
- `POST /api/tasks/:sourceId/merge` TaskMergeInput → source TaskDetail; close one task as a duplicate, exact versions and edit access on both endpoints
- `POST /api/tasks/:destinationId/merge-in` TaskMergeInInput → destination TaskDetail; atomically merge 1–100 selected sources, exact versions and edit access on every endpoint
- `GET /api/tasks/:id/mute` and `/mute/history` → the current person's private mute preference and paged history.
- `POST /api/tasks/:id/mute` → exact mute/unmute receipt, requiring View, write scope, Idempotency-Key and preference/access pins. No task Edit is required. See [task notification contracts](task-notifications.md).
- `GET /api/tasks/:id/subscriptions?after=PRINCIPAL&limit=N` → TaskSubscriptionPage; effective following membership, exclusive principal cursor, default 50, maximum 100
- `GET /api/tasks/:id/subscriptions/:principalId` → TaskSubscriptionStatus; includes absent preference version 0 and derived automatic following
- `POST /api/tasks/:id/subscriptions` TaskSubscriptionInput → TaskSubscriptionStatus; online-only preference update with expectedMembershipVersion, separate from task field versions
- `POST /api/projects` ProjectInput → Project; `GET /api/projects/:id` → ProjectDetail; `PATCH /api/projects/:id` UpdateProjectInput with expectedVersion → ProjectDetail
- Project alias resolution, paged history/members/watchers, separate join/leave and member collection changes, watching and private silence preferences: see the complete [project API contract](projects.md#api)
- `POST /api/repositories` `{name,remoteUrl,description?,defaultBranch?}` → Repository (registry only; no remote fetch)
- `POST /api/documents` DocumentInput → WikiDocument; `PUT /api/documents/:id` DocumentInput (expectedVersion required) → WikiDocument. Optional `message` records an edit summary; every edit appends immutable content history.
- `GET /api/documents/:id` → WikiDetail: current document, first 20 history summaries and activity.
- `GET /api/documents/:id/history?before=N&limit=N` → WikiHistory: summaries descending by version, exclusive `before` cursor, limit 1–100 (default 20), `nextBefore` and `firstAvailableVersion`. Missing versions and malformed cursors fail explicitly.
- `GET /api/documents/:id/versions/:number` → WikiVersion: immutable title, slug, content, author, timestamp, edit summary, kind and restored-from version.
- `POST /api/documents/:id/restore` `{version,expectedVersion,message?}` → WikiDocument: append selected historical title/content as a new version, retain the current slug and all historical records. Never queued offline; this is not upstream draft/publication-pointer behavior.
- `POST /api/revisions` CreateRevisionInput → RevisionDetail
- `GET /api/revisions/:id` → RevisionDetail
- `GET /api/revisions/:id/projects` and `/projects/history` → current visible project tags and bounded immutable history; independent project-tag version and current access epoch.
- `POST /api/revisions/:id/projects` → immutable changed/no-effect receipt for explicit `add`, `remove` or `set`; requires View, Edit, selected-project View, Idempotency-Key and project/access pins. Source versions and acceptance remain unchanged. Text/Git/Word creation accepts `projectIds` or legacy scalar `projectId`, never both. See [revision project tags](revision-projects.md).
- `GET /api/revisions/:id/metadata` and `/metadata/history` → current revision fields, exact source/configuration/access pins and bounded immutable edit history.
- `POST /api/revisions/:id/metadata` → immutable changed/no-effect receipt; requires View, Edit, Idempotency-Key and metadata/source/configuration/access pins. New text/Git/Word revisions and full metadata edits require `testPlan` by default. Existing sources and acceptance stay unchanged. See [revision metadata](revision-metadata.md).
- `GET /api/revisions/:id/subscriptions`, `/subscriptions/person?principalId=...`, and `/subscriptions/history` → visible follower pages, per-person subscription status and public history. `/subscriptions/mute-history` returns only the caller's private history.
- `POST /api/revisions/:id/subscriptions` → exact changed/no-effect receipt for subscribe/unsubscribe or self-only mute/unmute. Requires Idempotency-Key, preference/role/access pins and action-specific authority; source remains unchanged. See [revision following](revision-subscriptions.md) for pagination, permission and recovery contracts.
- `POST /api/revisions/:id/versions` CreateVersionInput → RevisionDetail; append immutable version and lifecycle history, invalidate acceptance and reject stale expectedVersion. Closed and Draft retain their status; other revisions return to Needs Review if review previously started, otherwise Draft. See [source-change lifecycle rules](revision-lifecycle.md#drafts-and-source-changes).
- `GET /api/revisions/:id/reviewers` and `/reviewers/history` → authorized reviewer state, exact source/configuration/evidence pins and paged immutable history.
- `POST /api/revisions/:id/reviewers` → exact immutable membership/decision receipt; requires Idempotency-Key and reviewer/lifecycle/author/source/evidence/configuration/access pins. Membership uses Edit; personal decisions use Interact. See [reviewer contract](revision-reviewers.md).
- `GET /api/revisions/:id/lifecycle` → current lifecycle/source/author/evidence/configuration/access snapshot and action availability.
- `GET /api/revisions/:id/lifecycle/history` → immutable paged manual/source/review transitions; supports `before`, `limit`, `expectedLifecycleVersion`.
- `POST /api/revisions/:id/lifecycle` → exact immutable action receipt; requires Idempotency-Key and source/author/reviewer/lifecycle/evidence/configuration/access pins. See [lifecycle contract](revision-lifecycle.md).
- Legacy `PATCH /api/revisions/:id` status requests now return 409; old saved receipt bytes remain but cannot prove a lifecycle action.
- `POST /api/revisions/:id/comments` CreateCommentInput → ReviewComment
- `POST /api/revisions/:id/threads/:threadId/replies` CreateReplyInput → ReviewComment; inherits the original thread anchor and records the viewed version
- `PATCH /api/revisions/:id/threads/:threadId` UpdateThreadInput → ReviewThread; current edit permission, optimistic thread version, exact source-version resolution provenance
- `POST /api/revisions/:id/suggestions/:commentId/apply` ApplySuggestionInput → RevisionDetail (201); explicit online application of a stored root-passage suggestion, exact current source/thread checks, atomic new version and immutable application record
- `POST /api/revisions/:id/reviews` ReviewInput → ReviewRun; hosted review explicit; errors never fall back to simulated AI. Reject stale input or revision changes during review.
- `GET /api/revisions/:id/export?version=N` → JSON snapshot `{revision,version}` (paper .tex downloaded from version.files in UI/CLI)
- Exact-version paper jobs, history, cancellation/retry and authenticated PDF/log/manifest/SyncTeX artifacts: see the [paper-build API contract](paper-builds.md#api).
- Exact-version reference inventories and source-File-gated reviewer attestations with append-only retractions: see the [citation API contract](citations.md#api-and-command-line). These explicit online mutations require an idempotency key and never enter the offline outbox.
- Paste snippets (`PA` IDs), source versions, raw text, history and version-bound comments: see the [Paste API contract](pastes.md#api). Mutations require an idempotency key and explicit online submission.

Both local and password modes bind to loopback with strict origin/host checks. The API does not execute source; explicit paper compilation uses the configured isolated worker. Password mode requires account membership for all content APIs. Object rules and restrictive Spaces further constrain access in both modes; see [policies](policies.md). See [authentication](authentication.md) for the credential and offline contracts. Include `Idempotency-Key` on client queued POST/PATCH/PUT; server persists successful mutation responses and rejects reuse for different bodies. This permits local-mode offline outbox replay without duplicates; password-mode drafts remain in tab memory and require reconnection to save. All writes and activity log events transactional. The local-mode client offline outbox supports tasks/documents/comments/versions, project metadata and basic project creation; don't queue hosted reviews, paper builds or acceptance.

`shared/review.ts` supplies `analyzeLocally(kind, files): ReviewAnalysis`; `server/ai.ts` supplies `analyzeWithAI(kind, files, provider?: 'openai' | 'ollama'): Promise<ReviewAnalysis>` and `aiConfiguration()`. Local review has real deterministic checks and is labelled local, not AI. Default fixtures are explicit demo content, seeded only for fresh DB unless disabled.

RevisionKind supports code, paper and document (general prose/legal draft). Local model review uses provider `ollama`, is explicit and requires OLLAMA_MODEL; no model downloads or implicit remote fallback.

Schema 2 migrates each pre-history wiki document into one `legacy` snapshot at its actual current version, with unknown author (`null`) and its existing last-edit timestamp. Earlier unavailable versions are not synthesized. New writes record an `attribution` containing principal ID, display name, credential ID and request ID; legacy records are not backfilled with fabricated verified authorship. Read/compare can use individually cached wiki versions offline (durable in local mode, tab-memory-only in password mode), but restoring requires a live current document.

## Authentication endpoints

- `GET /api/session` → `SessionState` (mode, workspace identity, optional account, session context, CSRF token, expiry). Anonymous password requests receive a pre-login challenge cookie/token; no content is returned.
- `POST /api/login` `{username,password}` → `SessionState`, after exact-origin and pre-login `X-CSRF-Token` checks; rotates the session cookie.
- `POST /api/logout` `{}` → anonymous `SessionState`; revokes the authenticated browser session and clears its cookie.

All protected cookie requests, including GETs, require `X-Session-Context`; mutations also require `X-CSRF-Token` and an exact matching Origin. CLI requests use `Authorization: Bearer …` with independent read/write/review scopes. Authentication, scopes and current object permissions are evaluated before any idempotency replay. Authenticated replay keys include workspace and principal; asynchronous reviews revalidate credentials and object permissions before committing under the write lock. Session and token secrets are never content-API fields. Auth responses are no-store.

Schema 4 introduced object and Space policies. Schema 5 adds review threads and immutable resolution events while preserving existing comment records. Schema 6 adds immutable suggestion applications. Schema 7 adds task versions, immutable transactions and directed dependencies. Schema 8 adds task ownership/authorship and subscription preferences without rewriting historical evidence. Schema 9 adds immutable duplicate links and single/batch merge transactions. Schema 10 migrates scalar task projects to canonical tag relationships without rewriting existing evidence; see [task contracts](tasks.md). Schema 11 adds project profiles, aliases, versioned members/watchers and private silence preferences, preserving legacy project data and adding project-specific join policies; see [project contracts](projects.md). Schema 12 adds project hierarchy and milestones; schema 13 adds workboards; schema 14 stores personal discussion collapse separately from shared threads. Schema 15 adds durable paper jobs and immutable artifact bytes without rewriting source, discussion or evidence. Schema 16 adds immutable Files and figure bindings; schema 17 adds immutable citation attestations and their separate retractions. Schema 18 adds Paste entities with immutable source versions and transactions while preserving existing entity row IDs and evidence. Revision details include threads, their events and suggestion applications; see [passage review](review-threads.md) and [suggested edits](suggested-edits.md) for their contracts. Previous binaries refuse the newer database. The separate durable authentication latch prevents a password-to-local downgrade. Account/session/token metadata is persisted separately from immutable document records.

## Access endpoints

- `GET /api/spaces` → visible `SpaceSummary[]`; `GET /api/spaces/:id` → visible `SpaceSummary`.
- `POST /api/spaces` `CreateSpaceInput` → `SpaceSummary`; `PATCH /api/spaces/:id` `UpdateSpaceInput` → `SpaceSummary`. Updates require `expectedVersion`.
- `GET /api/policies/:id` → `ObjectAccess`; `PUT /api/policies/:id` `SetPolicyInput` → current `ObjectAccess`. Updates require `expectedVersion`.
- All entity creation routes accept optional `access: NewObjectAccessInput`. Existing-entity content edits cannot silently change access rules.

Object capabilities describe policy rights; bearer operation scopes remain independent. Hidden/missing objects return `404` with `OBJECT_UNAVAILABLE`; forbidden operations on visible objects return `403` with `ACTION_FORBIDDEN`. Content/history reads, exports and retries use the same policies. Policy changes do not rewrite source snapshots. See [policy semantics and gaps](policies.md).

# Projects, hierarchy, membership and watching

Projects have stable `PROJ` identities, versioned profiles, globally unique aliases, members, watchers and an immutable transaction history. Their task lists use the existing many-to-many project tags. Archiving is reversible: an archived project remains readable, editable and usable as a tag, with an archived label and muted color. Archiving is distinct from deleting a project or restricting access.

## Profile and identity

Names, descriptions, status, icons, colors and aliases are editable with the profile's `expectedVersion`. An actual edit advances this version once and records old/new values. An unchanged request still checks access and the submitted version, but creates no event. Policy versions, membership versions and watch preferences are separate, so joining a project does not make an otherwise current description draft stale.

The initial catalog includes the 16 ordinary upstream icons and 10 colors. Existing custom hexadecimal colors are retained. A request may select either `colorKey` or a custom `color`, not both. Milestones always use the special milestone icon and their parent's color; their appearance cannot be overridden independently.

Ordinary project names generate a primary hashtag using upstream normalization: lowercase, separators become underscores, Unicode and hyphens remain, and the special names `.` and `..` become `dot` and `dotdot`. Aliases use the same normalization, are deduplicated, and have a 128-code-point limit. Rename retains the old primary hashtag as an alias, including when the same edit submits a replacement alias list. A later explicit alias edit can remove that old alias. Slugs are globally unique; collision errors do not identify an inaccessible project. Milestones have no generated primary hashtag: their `primarySlug` and `primarySlugSource` are null, and only explicitly supplied aliases enter the global slug index. Milestone names may repeat. Their display label is the immediate parent's name followed by the milestone name in parentheses, while the editable name remains unqualified.

Schema 11 adds profiles and relationships without rewriting existing project entity bytes, historical evidence or saved mutation responses. Old projects retain their names and custom colors. Their authors and timestamps remain unknown. A legacy transaction retains only the fields that actually existed. Migration reserves valid name slugs before assigning deterministic `legacy-proj…` slugs to conflicting or invalid legacy names, so no existing display name is silently changed.

## Subprojects and milestones

Ordinary projects can contain ordinary subprojects and milestones, with at most sixteen levels including the root. The kind and parent are fixed at creation: reparenting and converting an existing ordinary project into a milestone are unsupported. Milestones cannot have children. Each milestone receives a monotonically increasing number within its parent; archiving does not release a number. Parent renaming changes a milestone's current display label without rewriting its saved history or advancing its own metadata version.

The first ordinary subproject changes its parent from direct membership to the union of its ordinary descendant leaves. An explicit conversion preview records the complete member transfer count and pins the parent's metadata, hierarchy and membership versions. Confirmation copies every existing direct member into the first child, including disabled historical members, and adds any explicitly selected enabled members. Parent direct rows are retired as conversion bookkeeping. The resulting effective parent membership is preserved. Milestone creation does not trigger conversion. Later membership changes occur at ordinary leaf projects and propagate effective membership to their ancestors and milestones; direct join/leave and member-list edits are unavailable for derived membership.

Every child creation checks the three preview versions atomically. Concurrent hierarchy or membership changes require a fresh preview. Hierarchy changes have their own version and immutable transactions. Ordinary children default to their parent's Space but may use independent Space and policy rules. A child can be viewed only when its own access and every ancestor's view access permit it. A visible child's parent editors can edit it, but parent edit permission alone never grants child visibility. A milestone inherits its parent's Space and effective rules; its access controls link to the parent instead of offering independent policy edits.

Hierarchy lists, breadcrumbs, descendant task filters and membership provenance include only currently visible references. Permission changes invalidate descendant snapshots and hold unsaved drafts. First-child conversion cannot be undone by archiving children; archive affects only the selected project and leaves membership and hierarchy intact.

Schema 12 adds a canonical hierarchy table. Existing projects become ordinary roots without rewriting profiles, entities, historical snapshots or saved responses. New inherited or computed fields are not backfilled into old evidence. When a saved response no longer describes current hierarchy or membership, retry returns a content-free refresh receipt; it never attaches current descendants to the old result.

## Membership and access

Effective project members automatically have **view** access to their own project, subject to the containing Space and all ancestor projects' visibility. Membership does not automatically grant edit or interact access, and never grants access to tagged tasks. Projects have a separate **join** rule. Viewers may join when that rule permits them; project editors may join automatically. Existing members may leave. Editors may explicitly add, remove or replace the member list. Creation does not make the author a member unless the initial member list explicitly includes them.

Project rules can permit workspace members, selected principals, or members of that project. The last option is project-specific; it cannot be used as a Space rule or as an arbitrary project's access grant on another object. Every operation still requires the appropriate token scope. A Space remains an outer restriction, without an administrator or creator bypass.

For ordinary leaves, self join/leave uses the caller's membership-row version, initially zero. Derived membership exposes `version: null`, its source mode and visible source project IDs; it is never presented as a writable local row. An editor's add/remove/set operation uses the collection's version. Every actual membership change increments the collection once and advances the workspace access epoch atomically. Unrelated self joins may coexist; stale collection replacements fail as a whole. New membership grants require enabled accounts; existing disabled members may be retained or removed. No-op requests still check their versions.

Leaving or removing oneself can voluntarily remove access. A fresh authorized operation which removes the caller's view returns only `{id,saved:true,accessLost:true,accessEpoch}`. Saved retries recheck current authority and never restore an old view. Policy edits themselves continue to require retaining the editor's access.

The model preserves the upstream membership-lock flag, but this slice does not expose a lock toggle: upstream uses an application capability which is not implemented yet. It does not pretend that every project editor has that global authority.

## Watching and silence

Watching is independent of membership, grants no access and does not create individual task subscription records. Watching a project applies to its descendants, including through multiple ancestor levels. The viewer preferences distinguish their direct watch row, inherited sources and effective watching. An inherited-only watcher changes that preference at an ancestor; removing a direct watch does not cancel an inherited watch. An eligible viewer may watch or unwatch themselves. An editor may remove another watcher; adding another watcher is not supported. Each watch relationship has its own optimistic version.

Members can silence automatic project notifications without leaving. Silence is private to the member and is stored in a separate audit stream, outside public project history and activity. Watching can independently request notifications even when membership is silenced: the intended recipient set is `(effective members − silenced members) ∪ effective watchers`, further constrained by the delivery system's access checks. Tagged-revision updates now reach existing people watchers through the [revision notification inbox](notifications.md). Project membership alone does not subscribe a person to every tagged revision. Project-event delivery and email remain unfinished.

## Browser, offline and command line

Project profiles expose overview, tagged tasks, people, hierarchy, history and a [Workboard](workboards.md) link. Subprojects and milestones have separate lists and creation flows; first-child conversion requires its own confirmation. The project directory includes active/all, joined and watched views. Joined/watched views default to active projects. Archived tags remain selectable and clearly labeled.

Local-mode metadata drafts retain their exact project version and can queue offline. Basic local project creation can queue when it specifies no initial members or custom policy rules; the selected Space remains bound to the draft. Child creation, membership, watching, silence, policy changes and workboard writes require a live connection. Workboard move drafts retain exact board/task versions separately from metadata drafts; they never enter the offline mutation queue. Child drafts are bound to the parent and retain the exact preview versions; they are never queued as root-project creation. Password-mode drafts remain in verified tab memory and require reconnection to save. Permission changes discard old rendered project/task snapshots and hold unsaved work for export or discard. Late saves cannot erase a newer draft.

`npm run arc -- projects` lists active visible projects. `--status active|archived|all`, `--joined`, `--watching`, `--limit N` and `--json` are supported. Joined and watching filters intersect when combined. Joined includes effective membership; Watching lists direct watch preferences, with inherited watching explained in project detail. `npm run arc -- show PROJ1` returns the profile, the viewer's preferences and the first history page. Task `--project` filters accept a visible ID, exact name or alias (including `#alias`), and include visible descendants. Repeated filters require a matching tag in each selected subtree. Qualified milestone display names disambiguate repeated raw names. Hidden and missing projects fail alike. The configured server path prefix and read-only account tokens work for these reads.

## API

Shared request and response types are in `shared/projects.ts`.

| Route | Contract |
| --- | --- |
| `POST /api/projects` | `ProjectInput` → `Project` or a content-free access-loss/refresh receipt; optional initial members and project-specific access rules; child creation requires `parentId`, `kind` and the three preview versions, plus `confirmMembershipConversion: true` when required |
| `GET /api/projects/:id` | `ProjectDetail`, including visible hierarchy, history, viewer preferences, membership collection version and current access |
| `GET /api/projects/:id/children/preview?kind=project\|milestone` | `ProjectChildPreview` for a parent editor: pinned metadata/hierarchy/membership versions, conversion requirement and complete transfer count |
| `PATCH /api/projects/:id` | `UpdateProjectInput` with `expectedVersion` → `ProjectDetail` or a content-free access-loss/refresh receipt |
| `GET /api/projects/resolve?slug=…` | `ProjectDetail` for a normalized primary slug or alias, with the same visibility restriction as a direct read |
| `GET /api/projects/:id/history?before=N&limit=N` | `ProjectHistory`; exclusive sequence cursor, default 50, maximum 100 |
| `GET /api/projects/:id/members?after=PRINCIPAL&limit=N` | `ProjectMembersPage`; collection version and viewer preferences; exclusive principal cursor |
| `POST /api/projects/:id/members` | `{action:"add"|"remove"|"set",principalIds,expectedCollectionVersion}` |
| `POST /api/projects/:id/membership` | `{action:"join"|"leave",expectedVersion}` for the caller |
| `GET /api/projects/:id/watchers?after=PRINCIPAL&limit=N` | `ProjectWatchersPage`; exclusive principal cursor |
| `POST /api/projects/:id/watchers` | `{principalId,action:"watch"|"unwatch",expectedVersion}` |
| `GET /api/projects/:id/preferences` | Only the caller's membership, watch and silence states |
| `POST /api/projects/:id/silence` | `{silenced,expectedVersion}` for a current member |

Relation pages default to 50 entries and allow at most 100. Successful writes participate in the ordinary principal-scoped idempotency contract. Historical responses retain their original content and are presented under current authority. An old saved response lacking the current hierarchy contract returns a content-free `refreshRequired` acknowledgement rather than borrowing a newer profile. Current saved responses are also filtered under present ancestor access; saved content is never enriched from live descendants.

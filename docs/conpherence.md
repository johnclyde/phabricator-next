# Conpherence

Conpherence provides private conversations between active workspace accounts. A room has a title, topic, participants and durable, attributed messages. Its `Z` identifier, current version and transaction history remain stable across refreshes. Messages are authored by the authenticated sender, cannot be rewritten through the API, and never leave the server through an external messaging provider.

Create a conversation, choose participants and optionally write its first message. Participants may send replies, update the title and topic when allowed to edit, and manage the participant list. Participant changes update the room's member and editor policies together. The additional participant check applies even to the original owner: leaving or being removed revokes access. The last remaining participant must archive instead of abandoning the room. A person who has left can be added again by an existing participant; there is no public self-join route.

Read markers and archival are personal. Mark Read acknowledges only the saved messages visible at the selected version; it never marks a concurrently arriving message read. Read positions only advance, and each viewer receives only their own marker and archival state. Sending a message restores the sender's archived conversation but does not acknowledge messages the sender has not read. Other participants' archives are unaffected. The message panel initially renders the latest 50 messages and can reveal the entire earlier conversation without discarding messages.

Conversations update between connected clients without a manual refresh. An authenticated, same-origin long poll at `/api/conpherence/updates` returns only a policy epoch and a change flag; the client then reloads the current page through the ordinary policy-filtered API. Each pending request revalidates the original credential once per second and on its final check, expires after 20 seconds, and ends on disconnect or server shutdown. The process permits at most 256 simultaneous waiting requests; additional clients back off and retry. The client maintains one request at a time, pauses offline, retries failed polls with a delay capped at 30 seconds, and retires the transport on navigation or session changes. Successful idle heartbeats also refresh the page, so a failed content read recovers on a later heartbeat without requiring another message or a manual refresh. This does not require a separate WebSocket server or external messaging service. Unrelated workspace writes may also trigger an authorized refresh.

Permission changes retire previously displayed objects before reloading. Removing a participant or revoking their Space access removes the room from that client's view when the new epoch arrives. Session expiry ends the pending read. Reconnection retrieves current saved messages, but never submits a draft or retries an unconfirmed command. An open draft keeps its exact source version; incoming messages may make it stale, requiring explicit review and **Use Current Version** before sending. Unsaved text remains exportable after room access is lost and follows the existing session-scoped draft rules.

Messages and topics use the application's safe Remarkup reader for emphasis, lists, quotes, code and supported links. Exact source remains inspectable, executable HTML stays inert, and oversized or unsupported rich content falls back to its complete source. `@names` remain literal text; participant notifications do not imply directed mention support.

The application uses the shared suite API at `/api/suite/conpherence`: create `kind: "room"`, list, detail and versioned commands `message`, `read`, `archive`, `unarchive`, `edit`, `participants` and `leave`. Personal commands require current room visibility and an authenticated write credential; management commands also require current edit permission. Commands use the shared exact-version and idempotency protections. Space policy remains an additional requirement. No message is sent simply by reconnecting.

Historical references: `ConpherenceThread.php`, `ConpherenceParticipant.php`, `ConpherenceThreadParticipantsTransaction.php` and the pinned Conpherence editor/query implementation under `reference/phabricator`. The current implementation covers private membership, title/topic, persisted conversations, personal seen counts, native live refresh and the shared safe Remarkup subset. [Upstream XML imports](suite-import.md) create room metadata and explicitly chosen current participants; original messages, identities and read states remain separate historical evidence. This is not complete upstream parity: configurable public-room join policies, room pictures, attachments, directed mentions, email replies, durable-column chat, message/search indexing, full native reconstruction of historical conversations and complete Conduit compatibility remain gaps. The server returns a room's full saved message collection; scalable server-side message pagination is still needed for very large rooms. The common suite store currently limits a saved object to 2 MB, so a long conversation eventually needs to continue in another room. Personal archives are labeled in the list; a separate archive folder is not yet available. Live transport uses authenticated long polling rather than the historical Aphlict protocol.

Domain tests cover private policy, authoritative authorship, append-only messages, membership revocation (including original-owner leave), read marker monotonicity and projection, personal archives and permissions. Live transport tests cover authorization rechecks, timeout, cancellation, capacity, reconnection and late-response retirement. The common suite tests cover durable records, exact versions, authorization and replay. Browser tests exercise two signed-in clients, incremental updates, offline draft preservation, membership and Space revocation, and session retirement.

# Calendar

Calendar supports durable events with a host, description, location, timezone, invitations, attendance, discussions and cancellation history. Create an event with a local start and end in its IANA timezone, such as `2026-10-15T09:00` in `America/Los_Angeles`. Timed events are saved as exact UTC instants and displayed in their saved timezone. An explicit ISO timestamp with an offset is also accepted; the offset defines the instant while the event's timezone controls its display.

The responsive month grid and daily agenda show visible events and every generated recurring occurrence, including events spanning several days. Touch a date to inspect its agenda, follow an event link to its details, and navigate previous/next months or Today. The calendar fetches every visible page before reporting an empty day or a total; while loading it does not claim that a date has no events. Timed agenda entries use the browser's timezone, which is shown next to the grid. All-day dates do not shift across timezones. Access changes and session locking retire the entire in-memory inventory together.

Timezone conversion round-trips the local wall clock. A nonexistent time during a daylight-saving jump is rejected. A repeated wall-clock time is also rejected unless the author supplies an explicit offset, such as `2026-11-01T01:30-07:00`. The application does not silently move a meeting or guess which occurrence was intended. Edit Event prefills the event's local wall clock; repeated DST times retain their exact offset, and timestamps with seconds retain that precision. All-day events use date-only values and an exclusive end: an event occupying October 15 uses start `2026-10-15`, end `2026-10-16`. Real dates and an end after the start are required.

The host starts as attending. Editors can invite or remove people; reinviting an existing person preserves their RSVP. A viewer can record their own attendance or decline, including joining an event they can view. Nobody can submit an answer for another account. Invitations are application records and do not silently widen private object or Space permissions. Eligible participants receive current-policy inbox updates; [email delivery](notification-email.md) requires explicit account/object opt-in and an operator-configured mail service. Share private-event access separately before inviting someone who cannot see it. Event editors can cancel and reinstate an event without losing invitations, answers or comments. Cancelled events reject new RSVPs. Comments remain attributed and preserved when an event is rescheduled.

Daily and weekly recurring series require an explicit count of 2–366 occurrences, including the first. The author reviews a finite schedule, which is generated and saved atomically; there is no background recurrence expansion or invisible future work. Each generated date keeps the same local start and end clock in the original timezone, so UTC offsets may change across daylight saving. A DST gap or ambiguous later occurrence rejects the whole series with its occurrence number. Whole-minute times are required for recurrence. All-day series retain calendar-date boundaries.

Every occurrence has an independent attendance list and cancellation state. Respond to Event requires choosing the occurrence in a series. Invitation/removal actions apply to all generated occurrences, preserving existing answers when people are reinvited. Removal also includes people who joined only an individual occurrence without a series invitation. Reschedule One Occurrence retains both the original generated times and the override; other dates and answers do not change. Cancel One Occurrence and Reinstate One Occurrence affect only that date. Cancel Event cancels the entire series, while reinstating it preserves individually cancelled occurrences. The generated series schedule itself cannot be rewritten through Edit Event; that command changes shared title/description/location. Create a replacement series for a new repeating schedule. The immutable transaction history records each exception.

The shared suite API lives at `/api/suite/calendar`: create `kind: "event"` with optional `recurrenceFrequency` (`none`, `daily`, `weekly`) and `recurrenceCount`; list, detail and versioned commands `edit`, `invite`, `uninvite`, `rsvp`, `comment`, `cancel`, `reinstate`, `edit-occurrence`, `cancel-occurrence` and `reinstate-occurrence`. Occurrence commands and recurring RSVPs require the saved integer `occurrence` number. All commands require authenticated write authority and current object/Space visibility. Event management additionally requires edit permission. Exact versions and mutation idempotency are supplied by the shared store. Current policy is checked on every read and replay.

Historical references: `PhabricatorCalendarEvent.php`, `PhabricatorCalendarEventInvitee.php`, the Calendar event editor and cancellation/invitation transactions under the pinned `reference/phabricator` checkout. Implemented workflows cover individual events, finite daily/weekly recurrence with instance exceptions, a month grid and daily agenda, exact schedules, invitations and personal attendance, discussion, cancellation and reinstatement. This is not complete upstream parity. Unbounded/until-based recurrence, monthly/yearly rules, recurrence forking and future-series edits, host transfer, week/time-grid views, external invitees, iCalendar import/export/subscriptions, timezone preference profiles, drag-to-reschedule, project/status calendars, email replies, availability, complete Conduit compatibility and full historical reconstruction remain gaps. Current-policy following and inbox notifications, optional outbound email, and [upstream XML imports](suite-import.md) with separate RSVP evidence are implemented. Unsupported recurrence input is rejected rather than saved as a misleading one-off event. The common suite store's 2 MB object limit still applies to a complete series and its discussions.

Domain tests cover ordinary and fractional timezone offsets, DST gaps and repetitions, the Samoa date-line jump, all-day exclusive ends, leap-day recurrence, finite bounds, independent occurrence answers and cancellation, retained original exception times, date validation, host identity, re-invitation preservation, editor permissions, private-access preservation, cancellation/reinstatement and immutable comment attribution. Browser tests exercise two authenticated people using conversations and events on desktop and mobile. The shared suite tests cover storage, version conflicts, access revocation and idempotency.

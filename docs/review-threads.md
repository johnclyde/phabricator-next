# Passage review and discussion threads

Code, paper and prose revisions share an immutable review discussion model. A thread stays attached to the version where it began. Replies stay with that thread while recording the version the writer was viewing. Discussion is visible across versions, with Open, Resolved and All filters.

The typed/voice command `read discussion` reads counts and a bounded excerpt of up to three open threads, identifying their original versions and quotations. Individual thread navigation and narration use the same selection as touch and keyboard controls. Both use already-loaded, authorized content and no model call. Optional speech output uses only an available on-device voice. Spoken dictation and spoken resolution still require further workflow support.

## Personal collapse and navigation

Discussion cards are ordered by creation time, with their IDs breaking ties. Open, Resolved and All constrain the navigation list. Next/Previous controls and `n`/`p` move through expanded threads; `N`/`P` include personally collapsed threads without expanding them. Navigation stops at the ends. Previous with no selected thread does nothing. `q` toggles collapse for the selected thread. Shortcuts ignore editors, form controls, dialogs, composition, modified/repeated keystrokes and selected text.

Collapsing is a personal presentation preference, independent of resolving a shared thread. The compact header retains original source context, status and comment count. Reply and suggestion editors remain mounted while hidden, preserving their in-progress state. Navigation does not change the inspected source version, original anchor, resolution, source, acceptance or review evidence. Opening a thread's original version is a separate action.

Use `next thread`, `previous thread`, `next thread including collapsed`, `previous thread including collapsed`, `read current thread`, `collapse current thread`, or `expand current thread` as typed or spoken commands. Navigation to a collapsed thread reads its header only. Explicitly reading the current thread can read its bounded content while leaving it collapsed. Narration identifies the original version and reports shortened excerpts. Manual navigation, filters, source selection, route/session changes and access loss retire stale speech and private command feedback.

Saved collapse preferences belong to the authenticated principal and travel with that principal across devices. Viewing the revision is sufficient; edit or interact permission is unnecessary. A bearer token still needs write scope to save a preference. Current repository and Space visibility apply, including to retry receipts. Preference records do not appear in shared revision detail or discussion history.

Fresh online changes save against the last verified preference version. Offline changes affect local presentation only and never enter the mutation outbox. Reconnecting does not submit them. An uncertain request retains its exact body and request identity for explicit retry. Concurrent-device conflicts require attention; reloading saved preferences and choosing a new presentation is explicit. Local workspaces may retain presentation metadata on the device; protected workspaces retain it only in the verified tab. Access loss clears dependent presentation state as well as loaded source.

## Source anchors

A new passage comment records its original version ID and content hash, file path, half-open UTF-16 source offsets, exact quotation and bounded surrounding context. The server validates the submitted quotation against the immutable source and derives the stored quotation and context itself. Ranges cannot split a Unicode surrogate pair. The browser supports source selection and a line-range alternative for keyboard and touch use. General comments and existing single-line comments remain supported.

Projection into another version is a pure, local calculation; it does not rewrite the original anchor or use an AI model. A uniquely occurring exact quotation in the same file can be shown at its new position after an insertion or move. Multiple occurrences are marked ambiguous. Changed or missing passages and missing files keep the original quotation and an explicit explanation. The original source remains available through the thread's version link. Context is retained as evidence, not used to silently choose one repeated quotation over another.

These are precise source-passage anchors, not semantic paragraph identities. Renamed files, rebases and edited wording still need further mapping support. D106b adds comments on removed diff-side text by using its exact original base version, without cross-version mapping. Legacy line-only comments retain their original location without fabricated passage anchors.

Word revisions support separate exact main-story passage anchors with the package part, block, run range, offsets and original content hash. These anchors are never projected into another Word version. Replies, resolution, navigation and draft recovery use the same discussion model. An explicit [Word discussion export](docx.md#passage-discussion-and-word-comment-export) can add selected threads as classic comments in a separate DOCX without changing the original source or acceptance.

## Discussion beside a comparison

D106b is implemented and verified. Text comparisons offer distinct actions for an exact removed/base passage and added/target passage, and both line gutters can select their original source. A deleted file remains discussable on its base version. The selected pair stays fixed, including when its order is reversed. The shared anchor validator and existing server APIs enforce the original version, source quotation and range.

A single composer below the comparison serves both sides. Its **Comment version** selector restores independent version-scoped drafts and retains the selected destination when the reading pair changes. The composer remains available while another review tab is open. Saving pins its version and disables destination changes until completion; exact cleanup and private-review retry behavior preserve separate or newer drafts. The destination choice itself is not persisted: reload starts on the inspected target, with retained base drafts accessible through the selector. Existing local-mode storage and authenticated-session memory rules continue to apply.

Inline cards show at most 20 threads whose original version/hash/path and complete source anchor validate against the selected comparison. They contain the original quotation, a bounded root-comment excerpt and up to three recent replies. A visible count explains overflow; the complete all-version discussion remains available. **Open discussion** focuses its existing full thread and changes the discussion filter to All, leaving the comparison and personal collapse state unchanged. Read-only viewers can read and open these cards; comment creation still requires Interact permission.

The inline cards do not project anchors into newer versions or follow source-paragraph match links. Equal-version comparisons show an original thread once, on the target side. Legacy line-only comments and unavailable or mismatched anchors stay in the full discussion list. Word keeps its separate package-bound passage workflow. Historical suggestions remain tied to their original source and cannot apply to a later version. Multi-passage/file proposals, arbitrary selection across mixed diff text, inline reply editors, per-inline collapse and diff-order keyboard navigation remain unfinished. See [comparison contracts](comparisons.md#comments-edits-and-evidence).

## Replies and resolution

Messages are immutable. Each thread has its own optimistic version. A reply increments this version; resolving or reopening requires the version the caller actually saw, so a concurrent reply causes a conflict instead of silently closing unseen discussion. Successful retries with the same idempotency key do not add a second reply or event.

Resolution events retain the acting principal, credential/request attribution and exact source version being addressed. Resolving a thread does not accept a revision, produce review evidence or change source. New source versions preserve thread state and event provenance; a resolution on an older version is not a claim that later text was checked. A new reply does not implicitly reopen a resolved thread. Reopen it explicitly when further work is needed.

Replies require current view and interact permissions; resolution requires current view and edit permissions. Bearer credentials also require write scope. Reads, saved retry responses and writes under the database lock enforce current object/Space access. Resolution is online-only. Local-mode immediate comments and replies may be queued with their original anchor and version; authenticated unfinished edits remain in tab memory. [Private review drafts](review-drafts.md) separately support owner-only server staging, multiple independently edited entries, a complete preview, and atomic explicit publication. Their save/discard/publish requests are online-only and never automatically replay. Permission loss uses the same export/discard recovery behavior as other drafts.

## API and migration

- `POST /api/revisions/:id/comments` retains existing fields and accepts optional `passage: { start, end, quote }` with a `filePath`. `versionId` selects immutable source. A supplied line must agree with the passage.
- `POST /api/revisions/:id/threads/:threadId/replies` accepts `{ body, viewedVersionId }` and returns the immutable comment. The server inherits the root comment's anchor, original version and location.
- `PATCH /api/revisions/:id/threads/:threadId` accepts `{ status: "open" | "resolved", expectedThreadVersion, versionId }` and returns the updated thread. Stale versions and redundant state changes return conflicts.
- `GET /api/revisions/:id/discussion-preferences` returns only the caller's `{ revisionId, preferences, accessEpoch }`. Each thread preference contains `revisionId`, `threadId`, `collapsed`, `version`, and `updatedAt`. A thread without a saved preference defaults to expanded, version zero and a null timestamp.
- `PATCH /api/revisions/:id/threads/:threadId/preference` accepts `{ collapsed, expectedVersion }` and returns that caller's preference. The server derives the principal. A stale version conflicts even when the requested state already matches. With a matching version, repeating the current state is a no-op. Exact idempotent retries return their historical receipt; read current preferences to observe later device changes.
- Revision details include `threads` and `threadEvents` alongside the existing comments. Older comments without `threadId` are roots whose thread ID equals their comment ID.

Schema 5 adds threads and resolution history. Every existing comment becomes a one-message thread while its stored comment record remains unchanged, including attribution gaps. Database triggers reject updates and deletion of immutable comments and thread events. Migration and writes are transactional; earlier binaries refuse the new schema. Back up an existing workspace before upgrading.

Schema 14 adds only personal thread preferences. Existing threads, comments, versions, resolution events, evidence and saved response bytes are preserved. The preference version is independent of the shared thread version. The migration is transactional, and applications supporting only schema 13 refuse the upgraded workspace.

Saved schema-4 detail responses retain their historical comments. When replayed, their response shape includes corresponding one-message open threads and no resolution events; the stored response itself is unchanged. This describes the old snapshot, not current discussion. Fetch the revision again for current replies and thread versions. Optimistic version checks prevent a historical response from resolving subsequently changed discussion.

## Upstream relationship and gaps

The pinned upstream [Differential comment model](https://github.com/phacility/phabricator/blob/5720a38cfe95b00ca4be5016dd0d2f3195f4fa04/src/applications/differential/storage/DifferentialTransactionComment.php) supplies the range/reply model. Its [inline controller](https://github.com/phacility/phabricator/blob/5720a38cfe95b00ca4be5016dd0d2f3195f4fa04/src/infrastructure/diff/PhabricatorInlineCommentController.php) keeps replies at the parent's original anchor, and its [adjustment engine](https://github.com/phacility/phabricator/blob/5720a38cfe95b00ca4be5016dd0d2f3195f4fa04/src/infrastructure/diff/engine/PhabricatorInlineCommentAdjustmentEngine.php) projects old comments without rewriting the originals.

Upstream [Done/Undone authorization](https://github.com/phacility/phabricator/blob/5720a38cfe95b00ca4be5016dd0d2f3195f4fa04/src/applications/differential/controller/DifferentialInlineCommentEditController.php) has revision-owner and unpublished-draft semantics. This implementation uses current edit permission for immediate resolve/reopen. [Revision ownership](revision-authorship.md) and [private comment publication](review-drafts.md) are implemented separately; pending Done states and a combined comment/reviewer/lifecycle submission remain gaps. [Single-passage suggested edits](suggested-edits.md) now apply atomically to their exact original source version. Multi-passage/file proposals, semantic anchors and full cross-diff mapping remain unfinished. D101 and D106 are partial, and this slice does not establish Differential parity.

Upstream [changeset navigation](https://github.com/phacility/phabricator/blob/5720a38cfe95b00ca4be5016dd0d2f3195f4fa04/webroot/rsrc/js/application/diff/DiffChangesetList.js) supplies `n/p`, `N/P`, `q`, collapsed-selection and end-of-list behavior. Its [inline controller](https://github.com/phacility/phabricator/blob/5720a38cfe95b00ca4be5016dd0d2f3195f4fa04/src/applications/differential/controller/DifferentialInlineCommentEditController.php) stores hidden comments by viewer, and the [inline query](https://github.com/phacility/phabricator/blob/5720a38cfe95b00ca4be5016dd0d2f3195f4fa04/src/applications/differential/query/DifferentialDiffInlineCommentQuery.php) loads that viewer's hidden records. Upstream navigates individual inline comments in diff order. This implementation currently navigates whole chronological discussion cards across versions. Per-inline collapse and navigation in diff order, interleaving with changes/files, and the remaining upstream private-inline editing semantics remain parity requirements.
